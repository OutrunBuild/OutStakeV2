对全库已提交代码（`src/` 全量 + 与之直接相关的 `test/`、`script/`、`docs/spec/`、配置）做分批、多轮 Review。审查对象不是某次 diff，而是当前代码库本身的产品功能与实现细节。

核心铁律：Review-only，严禁修复。全程不得 Edit/Write 任何 `src/test/script/docs/spec` 代码或 `.harness` 配置；不得 `git add/commit/push`；唯一允许写入的是下述审查报告文档本身。被派发的 subagent 同样只读、不改文件、不跑修复命令。

审查单位与分批策略：
- 审查以「模块」为批次单位。仓库模块即 `src/` 的顶层子目录：`common / credit / governance / interoperation / polend / swap / token / verse / yield`。
- 每批覆盖一个或一组紧耦合模块（如 `polend` 与其 `test`、`docs/spec/polend` 一批；`swap` 与 `docs/spec/swap` 一批），以最小化跨批上下文重建。
- 批次顺序由依赖底向上：先 `common`，再 `token`，再各业务模块（`polend`、`swap`、`verse`、`yield`、`credit`、`governance`、`interoperation`）。每批独立多轮收敛。
- 批内主审查对象是 `src/<module>/**`；为核对影响，主会话与 subagent 可只读查看任何与之直接相关的既有 `src/`、`test/`、`docs/spec/`、接口、调用方与配置。
- 既有缺陷必须作为 finding 报告：可独立复现或能以严密状态推导证明的正确性、产品语义、不变量、权限、资金流或安全缺陷，一律纳入，不因「原本就这样」排除。

## Phase 0 — 全局建模（首轮前置，跨批复用）

任何模块进入分轮 Review 前，先对该模块完成正向建模，建立全局认知。建模产物作为后续所有角度的基线与交叉核对依据；缺失即无法进入 Phase 1，记录为阻断性缺口。

- 资金流图：列出该模块所有参与方（合约 / 账户 / 外部协议）与所有 token，每个动作在每条边上画出「谁付出、谁收到、数量表达式」，标明 source/sink。无 source/sink 的边立即标记。
- 数学模型：把每个被依赖的关键量写成表达式（含常量、fee、rate、share 等），写明变量取值域、单位（decimals）、舍入方向与舍入次数。只有自然语言、无数值表达式时标记缺口。
- 状态机：列出关键状态变量、取值域，以及每个动作的状态迁移；标明初始状态、终态、不可达状态、自环与回退。
- 路径空间：枚举合法调用顺序（含并发、重入、flash 还款、部分填充、退款/取消），并显式标注哪些组合被判为非法及判据。
- 不变量清单：列出模块声明的、或从语义可推导的不变量（守恒、会计对应、权限边界、单态性等），供后续角度逐路径验证。

建模产物以「模块」为单位并入报告的「模块认知」一节，跨批累积。

## Phase 1 — 分轮 Review（批内循环，每轮固定同一组角度）

每轮流程固定、角度固定、每轮全覆盖、不轮换。

### 1. 确定本批本轮审查对象

本批模块的 `src/<module>/**` 全量文件清单，加上与之直接相关的 `test/` 与 `docs/spec/<module>/**`。文件清单按路径传递给 subagent，不把源码贴进 dispatch prompt。

### 2. 并行派发 8 个 subagent（同一条消息并行，每个一个角度）

每个 subagent 先读 Phase 0 建模产物与本批文件清单，再仅返回 raw candidate dump（confirmed + borderline + rejected 及理由，三者均可为空）。允许空 dump：一轮中 confirmed 0 条、borderline 0 条是正常结果，直接返回空列表即可；严禁为凑数而制造候选。固定角度：

- A 文档-代码对齐：`docs/spec` 与实现是否一致；能否仅凭文档理解该模块全部产品功能与实现细节；反向检查代码中存在但文档未述的行为、事件、不变量、权限、边界。缺口必须定位到 `docs/spec::节` 与 `src::符号名` 的具体失配。
- B 可读性与注释：命名、注释充分性、初学者可读性。重点核对非显然的业务逻辑、不变量、跨步骤推理是否已有实现注释（NatSpec 不算）；是否使用了协议黑话而未在首次出现处解释。
- C 简化与冗余（代码优雅性：架构设计、可维护性）：可简化、死代码、重复逻辑、过度抽象（间接层/抽象粒度）、为单次使用而提取的琐碎 helper、未被请求的可配置项。以「资深工程师是否觉得过度复杂」为准；架构类建议必须给出具体收益（可审计性、drift 风险、成本），“更简洁”不构成收益。
- D 测试质量：无意义、冗余、重复或错误的测试；断言强度（空断言、只测 happy path、mock 掉真实不变量）；覆盖缺口（边界、回滚、权限拒绝、事件未断言）。区分「测了不该测的」与「该测没测」。
- E 正确性与边界：语义、边界（0 / max / 精度跨域）、状态转换、CEI 顺序、舍入方向是否偏向预期方。
- F Gas 优化：存储槽布局与打包、冗余 SLOAD/SSTORE、循环写存储、calldata 与 memory 选择、无实际节省的「优化」、可用 unchecked / 库函数 / 事件索引优化的点。标注预估节省量级，不报无节省项。Gas 候选必须带 static:/measured: 证据（移除/新增的 EVM 操作与净效果）；需 benchmark 或编译器输出才能判定的降为 candidate，不成 finding。
- G 安全漏洞：重入、整数溢出、访问控制、flash/unlock surface、升级安全、权限提升、预言机操纵、签名重放。
- H Bug：逻辑错误、状态错配、事件缺失或误发、不变量破坏、错误处理路径、外部调用失败未处理。

每个 subagent 的 dispatch prompt 必须显式包含以下约束：

「Review-only。不得 Edit/Write，不得运行修复命令，不得 git add/commit/push。先读取本批模块的 Phase 0 建模产物与本轮文件清单；可只读打开清单外、与本模块直接相关的既有 src/、test/、docs/spec/、接口、调用方与配置以交叉核对。本批 src 文件是主审查对象，但发现可验证的既有缺陷也必须返回。所有候选均须锚定 `文件::符号名`，引用基线代码片段，并给出 `输入/状态 → 错误输出/crash/revert/资金错配/权限绕过/不变量破坏` 的可验证触发路径或状态推导。候选须按 docs/prompts/finding-impact-scheme.md 定维度、定档并写出 Impact Statement；写不出 Impact Statement 或命中排除清单的候选放入 rejected 并注明理由。返回 raw candidate dump：confirmed、borderline、rejected；每个 rejected 必须附否决理由。不得遗漏已否决项。」

### 3. 本轮去重 + 验真 + 误报过滤（主会话执行，不轻信 subagent）

- 本轮去重：多个角度命中同一问题的合并为一，保留贡献角度列表。
- 逐条核对证据：贴出基线代码片段，给出可验证的触发路径或状态推导，锚定 `文件::符号名`。
- 影响评判：按 docs/prompts/finding-impact-scheme.md 锚表定维度、定档（Blocking/Major/Minor/Info），再按 Reachability（无条件/有条件/高门槛/假设路径）修正，只降不升。确认前必须写出 Impact Statement（谁 × 什么状态下 × 哪个维度 × 程度多大）；写不出 → 丢弃。命中排除清单（个人风格、行数削减、投机性 Gas、无证明的理论影响、不掩盖真实 bug 的测试覆盖缺口等）→ 丢弃并记录理由。既有缺陷（预存问题）与本批新引入的问题适用同一评判，不因位于基线而降档或丢弃。
- 误报过滤：对每条候选主动构造反驳——是否真违反不变量？触发路径是否可达？是否被上游检查 / 权限 / 已有断言阻断？是否只是风格偏好而无具体可证明的影响？
  - 无法自证为真、证据矛盾、无法建立触发路径、或仅凭风格偏好的候选，丢弃并记录理由。
  - Gas 候选必须给出实际节省证据（存储槽差、操作数差），否则丢弃。
  - 安全候选必须证明攻击者可控输入 + 可达路径 + 实际危害，否则降级或丢弃。
- 必要时运行只读 `forge build`、`forge test --match-path` 或 `grep` 交叉核对；不得修改代码。

### 4. 跨轮去重（finding 混合，不按轮分桶）

读取报告文档累积 finding 列表：
- 与历史 finding 语义等价的候选不重复写入。
- 历史 finding 是既有缺陷不构成排除理由；只有同一问题已被历史记录时才去重。
- 同一根因（同一底层缺陷）在本轮命中了新的触发条件、影响或修复落点时，不新增 finding，而是把新增的触发路径、影响与修复落点并入原 finding 的对应字段，发现轮次追加本轮，严重度取本轮与原 finding 的较高者并在「问题」栏注明衍生范围。
- 累积列表里的 finding 跨轮混排，只保留发现轮次与所属批次作为元数据。

### 5. 写入报告（追加，若没有则先创建）

追加到同一个中文文档：

```
docs/review/<YYYY-MM-DD>-codebase-multiround-review.md
```

`docs/review/` 已 gitignore，不影响 git。报告为累积单一结构，不按轮切片；每轮只把新增 finding 追加进同一列表并刷新批次表。结构见「Output Contract」。

## 停止条件

- 单批停止：该批内连续两轮「跨轮去重后且验真为真、过滤误报后」的新确认 finding 数均为 0。仅一轮为 0 不足以停止；中间任一轮出现新问题即重新计数。新确认 finding 计数只统计 Blocking/Major/Minor；Info（已证明但可忽略）不重置计数。
- 该批收敛后，进入下一批；Phase 0 对新模块重新建模。
- 全部批次收敛后，再跑一轮全库 cross-batch：以所有已确认 finding 为输入，专门寻找跨模块交互（调用方 / 被调用方 / 共享状态 / 共享 token）引入的新问题。该轮同样适用误报过滤。连续两轮 cross-batch 无新 finding 即整体停止（同样只统计 Blocking/Major/Minor）。
- 不得机械跑固定轮数；每轮须比上一轮深化，寻找前轮遗漏的新问题。

## Output Contract

最终输出使用中文，保留技术标识符、路径、命令与精确错误文本。按以下结构累积写入；没有内容的区块写「无」。

### 审查范围

- 审查起止时间、HEAD commit、覆盖的 `src/` 模块与文件计数。

### 模块认知（Phase 0 产物，按模块）

- 每个模块的资金流图、数学模型、状态机、路径空间、不变量清单，或标注「缺口」。

### 累积 finding 列表（跨批跨轮混合，不分组）

每条 finding：
- 编号；
- 所属批次与发现轮次；
- 贡献角度（A–H 中的一个或多个）；
- 严重度（Blocking / Major / Minor / Info）与 Reachability 级；
- Impact Statement：谁 × 什么状态下 × 哪个维度 × 程度多大；
- 问题；
- 证据：基线代码片段、`文件::符号名`、触发路径或状态推导；
- 建议修复方向（给方向，不改代码）；
- 修复落点文件。

### 文档对齐缺口（角度 A 汇总）

- `docs/spec::节` ↔ `src::符号名` 的失配清单，分「文档缺失」「文档与实现不符」「文档冗余」。

### 可读性 / 简化 / 测试质量摘要

- 分别汇总角度 B / C / D 的代表性问题，每条锚定 `文件::符号名`。

### 丢弃项摘要（误报）

- 本轮被过滤的候选、所属角度与否决理由；不得遗漏，用于证明误报已被识别和剥离。

### 批次收敛状态

- 每批：覆盖模块、已运行轮数、连续零新增轮数、是否收敛。

### 明确声明

- 每轮声明「本轮未修改代码」；后续轮次应深化寻找前轮遗漏的新问题。
